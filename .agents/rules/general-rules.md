# general-rules.md

任何任务都应阅读的**工作流规则**。编码规范见同目录下的专项规则文件。

## 通用规则

- 100%遵循用户提示词，不做用户没有明确指令要做的事。
- 必须遵循软件工程的最佳实践，包括代码质量、可维护性、可扩展性等。
- 一次只做一个原子任务，所以你需要拆分任务。
- 每个任务必须有明确的完成标准，达到预期标准才能交付给用户，严禁在过程中降低标准。
- 拆分任务时可以创建临时文档，用于记录子任务，用`- [ ] `来确认和标记子任务的完成情况。
- 单个会话结束前必须执行code review，否则不能交付。

## 架构与设计原则

- 现阶段可以质疑已有代码的架构和业务设计。
- 执行架构设计时必须调用 `superpowers` skill，并向用户询问未确认的设计方案。
- 设计未来前端有数据交互的模块时，必须结合当前业务和前端视角，设计出符合前端需求的接口和数据模型。
- 实现完整模块时必须编写单元测试，通过后才能交付代码。参考 `.agents/skills/write-service-test.md` 中的模板和速查表。
- 创建新 CRUD 模块时遵循 `.agents/skills/create-crud-module.md` 中的工作流和文件清单。
- Code Review 时使用 `.agents/skills/code-review.md` 中的结构化检查清单。
- 多模块联调时必须编写集成测试，通过后才能交付代码。如实现用户登录、认证、登出时必须设计集成测试跑通全链路。

## 编码规范索引

## CR 规则

- 执行code review时要考量以下因素：
  - 与已有架构的兼容性
  - 与目标业务的一致性
  - 可扩展性、可维护性、可测试性
- code review通过时必须告知用户完成标准和是否已达到。
- code review如不通过，终止当前任务并明确告知用户不通过及其原因，而不是继续执行。

## Git 规则

- 必须确认并切换到和当前任务相关的分支才能commit。
- 使用规范的commit message格式，包括类型（英文）、简短描述（中文）、详细描述（可选）。

## 文档规则

- 在`CHANGELOG.md`中记录开发进度和变更，格式遵循：
  ```
  ### YYYY-MM-DD
  **类型**：[Feature / BugFix / Refactor / Perf / Docs]
  **描述**：一句话描述
  **涉及文件**：列出变更文件
  ```
- 每次交付代码时必须同步更新 CHANGELOG，追加到"变更历史"节顶部。
